# 适配器协议

> **状态：草案。尚未实现。** 定下来之前不要开始写适配器。

## 为什么不能用现成的接口

现成 harness 的适配器是五个方法：

```python
add_chunk(content, timestamp)   finalize()
ask(question) -> str            retrieve_entries(question)   memory_count()
```

**它把记忆系统当纯函数**：喂进去、问出来、比对字符串。
[公开基准](../benchmarks.md) 全是这个形状，所以它够用。

[自研四类题](../suites/README.md) 一类都塞不进去，因为它们问的不是"你答得对不对"：

| | 需要什么，而五方法接口没有 |
|---|---|
| N1 对现实求值 | 一个 **harness 能改变的外部世界**，以及"哪些记忆不再成立"这个出口 |
| N2 原文回链 | 条目上的**来源区间**（起止），而 `retrieve_entries` 没有这一维 |
| N3 推理链 | **结构化的推导链**，而 `ask` 只返回字符串 |
| N4 治理 | **主体**——`ask(question)` 不带"谁在问" |

**这不是加参数能补的，是接口的假设不同。**

## 六条原则

### ① 能力自述，不靠试错

适配器**预先声明**支持哪些能力，harness 只跑声明过的套件。

没声明的记成 **不支持**，进独立的列，**永远不折进 0 分**。
把"做不到"和"做了但做错"记成同一个数，这把尺子第一天就废了
（[设计约束②](../suites/README.md)）。

### ② ⛔ 机制中立：协议只说要回答什么，绝不说怎么做到

这是**防主场优势的唯一手段**，也是最容易破的一条。

反面例子：如果 N1 的协议要求系统提供「断言」，那它就是照着某一家的实现写的——
有断言的系统赢，没有的输，而输的原因是接口偏心，不是能力差。

**正确的形状是给一个任务，不是给一个机制**：
> 这是一个世界。这些对话陈述了关于它的事实。世界随后变了。
> **你的哪些记忆已经不再成立？**

重读文件、调模型、跑断言、什么都行。harness 只看答案。

### ③ 世界归 harness 所有，适配器只读

被测系统**不得修改**世界。否则"通过"可以靠改变现实取得。
世界的构造与变更见 [`world.md`](world.md)。

### ④ 只走进程外接口

适配器通过**用户能用的方式**调用被测系统——HTTP / SDK / CLI，
**不得 import 它的内部模块**。

⛔ **这条对本项目作者自己的系统同样成立，而且首先针对它。**
一个能伸手进自己人内部的评测框架，公正性没法自证——
而这个项目的全部价值就在于它能自证。

### ⑤ 确定性判分，自研套件不用 LLM 评委

评委模型一换分数就漂。公开的 J 分已有前车之鉴：同一系统、同一数据集，
**84% / 58.44% / 75.14% 三个数**。

公开基准那边照旧用它们自己的判分代码——那是"同一把尺子"的前提。

### ⑥ 成本与延迟是一等指标

摄入 token、查询 token、墙钟时间，逐阶段记录。

一个赢 2 个百分点但贵 10 倍的系统，不写下来就看不出来。
[BEAM](../benchmarks.md) 是唯一这么做的公开基准，值得照抄。

## 接一个新系统要做什么

1. 声明能力（原则①）
2. 实现基线四方法——公开基准需要
3. 按声明实现对应套件的方法
4. 钉死被测系统的版本号（[五个已停更的项目](../systems.md)尤其重要）
5. 跑冒烟：确认"不支持"确实被记成不支持，而不是 0

接口定义见 [`protocol.md`](protocol.md)。
