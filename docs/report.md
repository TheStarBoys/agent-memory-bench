# 结果报告格式

> **状态：草案。** 这份规格的重要性不亚于[适配器协议](adapters/README.md)——
> 这个项目的全部价值是**可比性**，而可比性最终体现在报告长什么样。
> 一个把三态压成一列的报告，会把协议里所有的小心谨慎全部作废。

## 一句话原则

**报告的职责是让"分数低"和"没参加"看起来不一样，让"没做到"和"做不了"看起来不一样。**

## 一次跑的顶层结构

```json
{
  "run_id": "…",
  "at": "2026-09-01T12:00:00Z",
  "harness_commit": "…",
  "world": { "manifest": "…", "seed": 1234, "hash": "sha256:…" },
  "backbone": { "model": "…", "params": {} },
  "systems": [ { …见下… } ]
}
```

⛔ `world.manifest` + `world.seed` + `world.hash` 三个都要进报告。
少任何一个，别人复现不出同一个世界，两次跑的差就无法归因
（[world.md · 复现](adapters/world.md#复现)）。

⛔ `backbone` 必须是**全局一项**，不是每个系统一项——
跑 `answer` 档时所有系统共用同一个 backbone，否则分数没有可比性。

## 每个系统一块

```json
{
  "system": "mem0",
  "version": "v1.2.3",          // ⛔ 钉死，不写 latest
  "declared": ["ingest","search","answer","provenance"],
  "participation": { "declared": 4, "of": 8, "items_attempted": 3120, "items_total": 5840 },
  "suites": { … },
  "cost": { … }
}
```

### 声明与参与：`participation`

这一列专门堵[原则①的反向漏洞](adapters/README.md#p1)。

「不支持」不计入分母，于是少声明能力就能躲开难看的数字。**声明与参与让沉默可见**：
一个只声明了 `ingest`/`search` 的系统，分数栏可能很漂亮，
但声明与参与写着 `2 / 8`，读者一眼看得到它没参加什么。

⚠️ 声明与参与**不换算成分数、不加权、不排名**。它是一个背景数字，
不是又一个可以优化的指标。

## 每个套件一块：四列，不许合并

```json
"n2_provenance": {
  "status": "scored",
  "denominator": 1200,
  "scored":     { "回链率": 0.83, "精确匹配率": 0.61,
                  "IoU_p50": 0.94, "IoU_p90": 0.52,
                  "越界率": 0.18, "错链率": 0.07 },
  "failed_rate": 0.03,
  "unsupported": null
}
```

`status` 取五个值之一，**它们在对比表里占不同的位置**：

| status | 含义 | 在对比表里显示为 |
|---|---|---|
| `scored` | 跑了，有分 | 数字 |
| `unsupported` | 没声明这个能力 | **`—`**，⛔ 不是 0，不参与排名 |
| `partial` | 只有 N4 用：验到过滤层为止 | **`过滤级`**，⛔ 不是通过 |
| `untrusted` | `failed_rate > 0.20` | **`⚠`**，⛔ 不进对比表 |
| ⭐ `harness_fault` | **评测器自己**没跑成 | **`⛔框架`**，⚠️ 不是它的分，也不是它的错 |

⛔ **五个 status 永不折叠成一个数。** 这是[约束②](suites/README.md)在报告层的落地——
协议里分得再清楚，报告里压成一列就全白做了。

### ⭐ 臂这一层同样分四态

| 记在哪 | 含义 | ⛔ 别混的那一个 |
|---|---|---|
| `scores` | 跑完了 | — |
| `not_applicable` | 这条臂在这个语料上本来就没法跑（`full_context` 塞不下窗口） | ⛔ 不是跑挂了，⛔ 不是 0 |
| `crashed` | **被测系统**跑挂了 | ⚠️ 静默消失会被读成「没参赛」 |
| ⭐ `harness_fault` | **我们**没跑成 | ⛔ 不是 `crashed` |

⚠️ 最后一条是实测踩出来的：N4 第 3 步要重开一个实例验「重启之后还在不在」，
而 mem0 的 Qdrant 本地模式不允许两个客户端同时开同一个目录——
⛔ 整条臂被记成「跑挂了」，**而它什么都没做错**。
⭐ 那一列一混有两个后果：读者以为这个系统不稳，
**而我们自己的 bug 被盖住了**。

⛔ 它必须**显式抛出**（`core.HarnessFault`），⚠️ 不按异常类型猜——
猜错的两个方向都很糟：把我们的 bug 记成它的错，或者把它的错洗成我们的。

## N1 要六格全出

派生率**不得单独出现**，必须与矩阵同屏：

```json
"n1_reality": {
  "triggered": {
    "matrix": { "holds→holds": 410, "holds→broken": 22,  "holds→unknown": 68,
                "broken→holds": 91, "broken→broken": 240, "broken→unknown": 69 },
    "检出率": 0.60, "误报率": 0.05, "弃权率": 0.15
  },
  "spontaneous": { "status": "unsupported", "reason": "Entry.doc_ids 为空" }
}
```

⛔ **有提示与无提示分开报，永不合并**——一个是"给了机会你查得准不准"，
一个是"没人提醒你自己发现了吗"，合并之后两者都读不出来。

⛔ 只报检出率的表是**坏表**：一个把所有命题都标 `broken` 的系统检出率 100%。
误报率、弃权率、六格原始计数，一起出现才有意义。

## 两个钩子分列

```json
"locomo": {
  "search": { "recall@10": 0.71 },
  "answer": { "f1": 0.58, "backbone": "…" }
}
```

`search` 量的是**记忆层的召回质量**，署名 `<系统>`；
`answer` 含答案生成器，署名 `<系统> + <backbone>`。
只报后者是把别人的生成器算进自己的成绩。

## N5 / N6 / N7 各有一条不许省的伴随指标

三个新套件都有「只报一半就能刷分」的结构，报告层要挡住：

```json
"n5_consolidation": {
  "observed": {
    "保留追踪度": 0.61,
    "矩阵": { "该留-留了": 820, "该留-丢了": 140,
              "该丢-留了": 610, "该丢-丢了": 90 },
    "因子": { "频率": 0.44, "间隔": 0.03, "显著性": 0.51 },
    "检索加固": { "长间隔": 0.12, "短间隔": -0.04 }
  },
  "self_reported": { "status": "unsupported" }
},
"n6_structure": {
  "可达性": { "fan1": 0.42, "fan2": 0.55, "fan4": 0.68, "fan8": 0.79, "fan16": 0.83 },
  "精确检索": { "fan1": 0.91, "fan2": 0.84, "fan4": 0.71, "fan8": 0.55, "fan16": 0.38 },
  "扇形退化斜率": -0.13
},
"n7_calibration": {
  "ECE": 0.14, "Brier": 0.21,
  "可靠性图": [[0.1,0.08],[0.3,0.22],[0.5,0.41],[0.7,0.52],[0.9,0.61]],
  "区分度": 0.29,
  "显著性子测": { "普通-准确率": 0.55, "普通-置信度": 0.58,
                  "显著-准确率": 0.56, "显著-置信度": 0.81 }
}
```

| 套件 | ⛔ 单独报会被刷的那一半 | 必须并列的 |
|---|---|---|
| **N5** | 只报「该留的留了」→ 从不遗忘的系统满分 | **该丢的丢了没有**（四格矩阵） |
| **N6** | 只报可达性 → 连成完全图的系统满分 | **精确检索退化曲线** |
| **N7** | 只报 ECE → 把置信度压到基准准确率附近就能拿低 ECE | **区分度 + 可靠性图** |
| **N8** | 只报三个问题的总正确率 → 两种相反的毛病并成一个数 | **四种行为分列** |

N8 的四种行为要各占一格，⛔ **不许汇总成一个准确率**：

```json
"n8_induction": {
  "行为": { "全对": 210, "过度修正": 96, "过度泛化": 141, "未归纳": 353 },
  "规律强度单调性": 0.34,
  "推导链一档": { "status": "unsupported" }
}
```

⚠️ 「过度修正」（一个反例就把规律扔了）与「过度泛化」（规律压过明确的例外）
**是两种相反的失败**，改进方向也相反。在只判对错的表里它们都是「答错一道题」,
合并之后读者看不出该往哪个方向修。

⛔ **这三条与 [N1 的六格](#n1-要六格全出)是同一条纪律。**
判分口径定得再仔细，报告里只印一半，作弊面就重新打开了。

⭐ **N7 显著性子测里，「准确率相同而置信度显著更高」是失分项**，
不是中性观察——它复现了闪光灯记忆那个已知的人类 bug
（[cognition.md](cognition.md)）。报告要把这一格标出来。

## ⛔ 抽样分必须带区间

⭐ [抽样方法论](sampling.md)在报告层的落地：
一个不带区间的抽样分是在骗人——它假装自己是全量分。

```json
"locomo_retrieval": {
  "status": "scored",
  "scored":   { "evidence_recall": 0.522 },
  "interval": { "low": 0.385, "high": 0.652, "n": 50, "half_width": 0.133 },
  "detectable": 0.264,
  "sampling":  { "strategy": "stratified", "seed": 42, "sampled": 50,
                 "total": 1986, "by_stratum": {…} }
}
```

| | ⛔ |
|---|---|
| `interval` | 只给点估计的抽样分**不许出现** |
| `detectable` | 这个 n 下最小能分辨的差异——⛔ 差异小于它就不许说「A 比 B 好」 |
| `sampling` | 策略与种子——⚠️ 不记的话两次跑的差可能全来自抽到了不同的题 |

### ⛔ 区间重叠时不许排名

对比表里两条臂的区间重叠，就**不给高下**：

```
| bm25 | 0.522 [0.385, 0.652] |          | 地板 |
| mem0 | 0.610 [0.470, 0.735] | ⛔ 分不开 | 差 0.088，但 n=50 只能分辨 ≥0.264 |
```

⚠️ 那不是「一样好」，也不是「mem0 更好但不显著」——
是**这次跑答不了这个问题**。要答就加题：见
[要多少题](sampling.md#how-many)。

## ⛔ 两档分开报

一次跑可能含两档，⛔ **它们的数不可互比**：

```json
"lanes": {
  "library": [ … ],   // 直接调库：评测器主动 search
  "agent":   [ … ]    // 装进 agent：agent 自己决定何时检索
},
"host": { "version": "0.1.2a3", "profile": "sdk" }
```

⚠️ `host.version` 必须进报告——**换 DSH 版本等于换尺子，要重跑全部基线**。

⭐ agent 档多两个成本项，与分数并排读：

| | 量的是 |
|---|---|
| `memory_calls` | agent **主动**查了几次记忆——直接调库那一档量不到 |
| `agent_steps` | 走了几步才答出来 |

## ⛔ 每个分数都要跟着地板线

绝对分单独出现是没有意义的。一次跑里，[五条对照组](baselines.md)
与被测系统**同批次、同世界**跑，报告里每个套件的分都带三样东西：

```json
"n5_consolidation": {
  "floor":   { "arm": "host-default", "保留追踪度": 0.31 },
  "scored":  { "保留追踪度": 0.61, "Δ": +0.30 },
  "cost_ratio_vs_floor": 2.8
}
```

| | 说明 |
|---|---|
| `floor.arm` | 该档**最强**的地板线，⛔ 不许挑最弱的那条来抬高自己 |
| `Δ` | 相对地板的增量——**这才是记忆系统的贡献** |
| `cost_ratio_vs_floor` | 贵了几倍，⭐ 必须与 Δ 一起读 |

⚠️ **Δ ≤ 0 要显式标注**，不能只是「分低一点」——那意味着帮了倒忙。

⛔ **不得引用历史批次的地板线。** 地板线随 backbone、宿主版本、世界一起漂，
拿旧地板配新成绩，Δ 就是假的。批次号进 `run_id`。

## ⭐ 成本 × 质量：并排判，⛔ 不给总分

一次跑里，成本与质量出现在**同一张表**，按[原则⑥](adapters/README.md#p6)给帕累托判定：

```
| | 质量 | Δ vs 地板 | 总耗时 | 每条摄入 | 每次回答 | 判定 |
| good | 0.700 | +0.180 |  1.0x | 0.00s | 0.15s | ⭐ 又快又好 |
| mem0 | 0.610 | +0.090 | 4480x | 36.7s | 2.00s | ⚠️ 更准但更贵 |
| slow | 0.950 | +0.430 | 1802x | 0.02s | 45.0s | ⛔ 慢到不可用 |
| bad  | 0.400 | -0.120 |   16x | 0.08s | 0.15s | ⛔ 被地板压制 |
```

⭐ **质量最高的 `slow` 被判不可用**——回答一次 45 秒，记得住也救不回来。
⛔ `bad` 既不如地板准又比它慢，**没有存在理由**。

⚠️ 质量轴取**参与面最广**的那个套件——
挑一个大多数臂都不支持的，成本表就只剩一行，比较不起来。

## 成本与延迟（原则⑥）

```json
"cost": {
  "ingest": { "tokens_in": 1.2e7, "tokens_out": 3.1e5, "llm_calls": 8400,
              "wall_ms_self": 902000, "wall_ms_harness": 951000 },
  "probe":  { … },
  "source": "adapter"      // 或 "harness_only"：系统没声明 ACCOUNTING
}
```

⚠️ 墙钟**两份都记**：`wall_ms_harness` 由评测器从外部独立计时，
`wall_ms_self` 由适配器自报。两者差得多本身就是信息（排队、重试、后台补偿）。

⚠️ token 只有适配器报得出来。没声明 `ACCOUNTING` 的系统 `source` 记
`harness_only`，token 栏留 `null`——⛔ **不是 0**。

## 利益关系必须标注

| 情形 | 标注 |
|---|---|
| 题库由某被测系统的作者维护 | 该系统在该题库上的成绩标 `⚑ 利益关系` |
| 适配器由被测系统的作者提交 | 标 `⚑ 自提适配器` |
| 被测系统是本项目作者的 | 标 `⚑ 自有系统`，且**必须**标 |

已知的第一类：**`memorybench` 由 supermemory 维护，而 supermemory 是被测系统之一**
（[benchmarks.md](benchmarks.md)）。

标注不是指控，是让读者自己判断。一个不标注利益关系的评测框架，
和一个伸手进自己人内部的评测框架，失去公信力的方式是同一种。

## 上游判分的已知缺陷

公开档一律用上游的判分代码（[纪律](benchmarks.md)），但上游判分有已知问题时，
报告必须带一段 `upstream_notes`，逐条写明缺陷与影响。
政策见 [harnesses.md · 上游判分坏了怎么办](harnesses.md#上游判分坏了怎么办)。
