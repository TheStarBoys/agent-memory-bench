# 怎么让贵的系统跑得起来（⛔ 不关 LLM）

> 实测：mem0 摄入 **9.7~10.0 秒/条**（四次跑），占总耗时 **83%**。
> ⛔ 关掉 LLM（`infer=False`）能快 **7~10 倍**，但那是**换了个被测对象**。
> 这里说的是**不动被测系统**的办法。

## 三条路，只有两条安全

| | 收益 | 安全吗 |
|---|---|---|
| ⭐ **摄入快照** | 重跑问答**免费** | ✅ 完全安全 |
| ⭐ **LLM 响应缓存** | 重跑同一批语料几乎免费 | ✅ 安全，⚠️ 但要标注 |
| ⭐ **续跑** | 中断之后不用从头来 | ✅ 安全，⛔ 键对不上就拒绝 |
| ⛔ **并发摄入** | 理论上 10–20 倍 | ⛔ **不安全——见下** |

---

## ⛔ 为什么并发摄入不能用

摄入是 I/O 密集的（CPU 实测 0.6%，全在等网络），所以并发看起来是白捡的加速。

**⛔ 但对归并型系统它不成立。**

mem0 的 `add()` 要拿新事实和**已有记忆**比对，裁决 ADD / UPDATE / DELETE。
并发时每个调用看到的库状态不同 → **归并决策就变了** →
⚠️ 那不是同一个系统跑得快了，是**另一个系统**。

⭐ 判据很清楚：

> **摄入结果依赖已摄入内容的系统，⛔ 不能并发。**

⚠️ 纯索引型（bm25、朴素 RAG、`mem0_raw`）可以并发——
但它们本来也不慢，⛔ 并发对它们没意义。

---

## ⭐ 跑前自检：⛔ 不花钱就能发现的错，不许等到花完钱才发现

**最贵的浪费不是跑得慢，是跑完才发现这一跑不算数。**

[2026-09-03 那天](runs/README.md)连交两次学费：一次 2h45m 的跑，报告最后
印出一句假话（`null` 当上质量轴地板，四条真臂全被判「没有存在理由」）；
另一次 2h45m 的跑，语料本身造错了，**全废**。

⚠️ 而这两次的成因**没有一个需要真跑才能发现**——
它们全是**题面 · 判分 · 报告**这三层的性质，
⛔ 与被测系统、与 LLM、与 embedding 端点一点关系都没有。

```sh
python -m amb.cli preflight --bench dialogue --condition revised \
    --arms null,bm25,naive_rag,mem0_raw,mem0
```

⭐ **零网络调用**，实测 toy 3 秒 · dialogue 1 秒 · LoCoMo 21 秒。
⚠️ 每次正常跑**自动执行**，⛔ 有致命发现就不开跑（`--skip-preflight` 强跑）。

### 它查什么——⛔ 每条都对着一次真实付过的代价

| 检查 | 当初付了多少 |
|---|---|
| `query-is-identity` | N6 精确检索拿**整句**去查——那是恒等式，⚠️ 所有臂恒 1.000，一次真跑才发现 |
| `query-is-substring` | N6 三个线索全是原文子串——⛔ 量的是字符串匹配，加大扇形度白干 |
| `gold-missing` | LoCoMo 13 道题的证据不在语料里——⚠️ 任何系统都不可能命中，**假的失分** |
| `doing-nothing-wins` | 退化斜率当质量轴——⛔ `null` 每档 0.000，斜率完美等于 0，于是它赢了 |
| `unpublishable-headline` | N5 占位曲线当质量列 |
| `verdict-on-flat-metric` | 质量列分不开各条臂，报告却仍在下判定 |

⭐ 手法是**录制**：拿一个只记查询、不给结果的适配器把所有套件跑一遍，
⛔ 不需要套件配合就能拿到它**实际会发出**的每一条查询——
⚠️ 让套件自己申报的话，申报与实际会漂移，而漂移正是要查的东西。
判分那几条则是拿 `null` 与 `bm25` 两条**离线**臂走完整条判分 + 报告链路。

### ⛔ 它查不到什么——这一条必须写在前面

「摄入单元读起来像不像一轮真对话」**自动查不了**。
⚠️ 那次全废的语料是十条互不相干的短句拼够了长度，
⛔ **所有数值检查都过**——因为长度是「像一轮对话」的代理，不是它本身。

⭐ 所以自检**强制打印样本**：查不了的，就摆到眼前逼人看一眼。
⛔ 不要因为「有 preflight 了」就跳过这一眼——它恰恰是唯一挡得住那类错的东西。

### ⚠️ 为什么两条查询检查只是警告

N5 **故意**拿原文当查询（它问的是「给你原文你还找不找得到」，那是保留度
不是检索难度），N2 的查询本来就是原文的一段。
⛔ 一刀切成致命就会每次刷屏，⚠️ 而刷屏的结果是人开始忽略它——
⭐ **那正是原来那些 bug 溜过去的方式**。
所以它们归因到**套件**，判断权交给读的人，⛔ 但必须说得清为什么可以放过。

## ⭐ 摄入快照：贵的那一步只做一次

摄入对**同一份语料 + 同一个系统 + 同一个 backbone** 是确定的。
存下来，重跑问答就免费。

⛔ 快照键必须覆盖所有影响摄入的东西：

```
系统名 + 系统实际版本 + backbone + 语料指纹（含顺序）
```

⚠️ **顺序也算进指纹**——归并型系统对摄入顺序敏感。
⛔ 漏掉任何一项都会拿错快照，而那比慢更糟：**它会静默给出别的系统的分**。

⚠️ 写完才落 `.complete` 标记——⛔ 半截快照比没有更糟。

**适用**：改判分口径、加套件、调抽样——这些都不动摄入。

### ⛔ 但**跑了 N4 的那一跑存不下快照**

快照是在 `close()` **之后**拷目录的（子进程还开着 qdrant 时拷会拷到半截），
⚠️ 而那时探针已经跑完了——[N4 治理档会真的删条目](suites/n4-governance.md)。
⭐ `run_one` 会拿摄入完那一刻的行为指纹对账，对不上就**不存**：
一份被删过东西的 store 不代表「摄入完的状态」，⛔ 存了下次就会拿到错的库。

⚠️ 后果说清楚：**带 N4 的 toy 全跑，`mem0` 那 **70 分钟**摄入每次都要重付。**

| 想省这一步的办法 | ⛔ 代价 |
|---|---|
| 摄入完立刻 close 再拷，然后重开 | ⚠️ 探针从此跑在一个「重开过」的库上——⭐ 那更贴近现实，⛔ 但它改变了所有臂的测量语义，且与 N4 第 3 步（重启即现原形）撞车 |
| 不跑 N4（`--arms` 里去掉声明 GOVERNANCE 的臂） | ⛔ 等于不测治理，⚠️ 而那是自研套件里判别力最强的一类 |
| 只在迭代评测代码时跳过 N4 | ⭐ 这个可以，⚠️ 但出可信数字的那一跑必须带上 |

⛔ **不要为了存快照而把 N4 的删除探针改成「只读」**——
那正是这一类要批判的「过滤不是删除」。

### ⭐ 对照臂也在快照里（⚠️ 但省的不多）

`naive_rag` / `hybrid` 早先拿不到快照，代码里写的理由是
「对照组没有外部版本号——它们摄入本来就便宜」。

⭐ **那句话是对的**。2026-09-07 实测 toy 623 篇：

| | 墙钟 | 占比 |
|---|---|---|
| 整条臂 | 1303s | |
| ⭐ 摄入（快照能省的） | **112s** | **8.6%** |
| 探针 | 1191s | 91.4% |

⛔ 一度以为是「1386 秒」并据此推翻那句原话——⚠️ 那是**整条臂**的墙钟，
不是摄入。⭐ 口径搞错了，结论就反了。

⚠️ 更要紧的是 embedding 花在哪：**总墙钟 1050s，摄入只占 112s**，
剩下 **938s 是探针里每道题一次的 query embedding**（204 题，最慢一次 4.1s）。
⛔ 而快照救不了那部分——它只冻摄入。

**所以为什么还要做？** ⭐ 不是为了省时间，是为了**口径一致**：

⚠️ 「命中快照」会改变一条臂的耗时构成。⛔ 只有被测系统能命中、
对照臂不能，那么「快照命中与否」本身就成了臂之间的一个差别——
⭐ 而这个评测的全部前提是**差别只来自记忆层**。

技术上的两个阻碍：

| 阻碍 | 怎么解决 |
|---|---|
| 快照是**拷目录**，而它们只活在内存里 | ⭐ 落一份 `index.json`（切块 + 向量 + 分词 + df） |
| 版本号那一格没有外部依赖可填 | ⭐ 用**评测器自己的代码指纹**（`code:<digest>`） |

⛔ 用代码指纹当版本号意味着**改一行代码，全部对照臂快照作废**。
⚠️ 这是刻意的：向量是用那份代码算出来的，切块或归一化一改，
旧向量就不再对应新口径——⭐ 而那种错**算得出分，不报错**。
⚠️ 代价只有 112s，所以这笔交易划算。

### ⛔ 想省探针那 938s？现在没有安全的办法

⚠️ query embedding 不缓存也不快照。⛔ 缓存它会把「同一道题问两次」
变成一次真调用加一次回放——⭐ 而延迟数字会因此不可信。
⚠️ 这一条**没有解**，是这个评测已知的成本地板。

## ⭐ 续跑：一次几小时的跑不该是全有或全无

⛔ 实测踩到：跑到第 5 条臂被系统 OOM 杀掉，前面 4 条臂 42 分钟的结果
**全部丢失**——⚠️ 因为 CLI 只在**全部跑完**才写 `--json`。
（⭐ 那次 `naive_rag` 1386s、`mem0_raw` 1142s，⚠️ 这两个是**整条臂**的墙钟，
⛔ 不是摄入耗时——摄入快照救不回它们，只有续跑能。）

⭐ 现在**存档本身就是检查点**：每条臂跑完立刻写进同一个 `--json` 路径，
下次启动读回来、跳过已经跑完的那几条。

```sh
python -m amb.cli --bench toy --arms null,bm25,naive_rag,mem0_raw,mem0 \
  --json out/toy.json          # ⭐ 中断后原样再跑一次就是续跑
python -m amb.cli ... --fresh   # ⛔ 明确要求从头来
```

⛔ 不另造一种检查点文件格式：⚠️ 那会多出一份要与存档同步的东西，
而「两份迟早不同步」在这个仓库里已经出现过好几次。

### ⛔ 什么情况下**不许**续跑

续跑的前提是「接着跑出来的分与已经跑完的那几条**可比**」。
⚠️ 键里任何一项变了，就**大声说出来并从头跑**，⛔ 绝不静默混用：

| 变了什么 | 为什么不能续 |
|---|---|
| **判分/套件的代码** | ⛔ 新口径的分与旧口径的分并排放，就是「新表格配旧数」 |
| 语料指纹 | ⚠️ 题都不是同一批了 |
| backbone / 摄入身份 | ⛔ 换了模型等于换了被测对象 |
| 答题口径 | ⚠️ 提示不同就是两套实验 |
| 抽样 provenance | ⛔ 抽到的题不一样 |
| `--budget` | ⚠️ 它决定 `full_context` 是 N/A 还是有分 |

⚠️ 代码指纹严格到「动一个注释也不给续」——⛔ 分辨「这次改动影响不影响
判分」需要判断，而判断会出错；⭐ 从头跑只是慢，混用是错。

⚠️ 代价说清楚：**一次跑在飞的时候不能改 `src/amb/` 或 `worlds/`**，
改了就续不上。⭐ 这条限制是我们选的，不是漏掉的。

### ⚠️ 粒度是**一条臂**，不是一道题

⛔ 臂内中断（比如 `mem0` 摄入到一半）仍然要从这条臂的头开始——
⭐ 但摄入快照会兜住它：那条臂上一次**跑完过**的话，这次直接命中。
⚠️ 两层合起来才是完整的：**快照省摄入，续跑省整条臂**。

## ⭐ LLM 响应缓存：内容寻址

缓存键是 `(模型, 全部参数, 完整请求体)` 的哈希。
同样的输入本来就该得到同样的输出。

```sh
AMB_LLM_CACHE=1 python -m amb.cli --bench locomo --arms mem0
```

⛔ **默认关闭**——打开它的跑不是一次独立的延迟测量，得有人明确要求。

### ⛔ 两条硬规矩

**① `temperature > 0` 时不缓存。** 那会把随机性冻成一个固定答案——
⚠️ 系统本来会给出分布，缓存让它只给一个点。

**② 缓存命中率进报告。** 命中 90% 的跑测出来的「延迟」不是真延迟。
⛔ 不标出来，「它变快了」会被读成系统变快了。

**⭐ 实测（mem0，`infer=True`，⛔ 没关 LLM）**：

    冷缓存  82.0s   调用 1  命中 0
    热缓存   2.7s   调用 1  命中 1   ⭐ 省下 78 秒，快 30 倍

⚠️ 剩下的 2.7 秒是 embedding——那个不缓存，也不该缓存（它便宜）。

### ⭐ 「缓存为什么没生效」现在自己会说

命中率为 0 有很多种原因，⛔ 不分开记就查不出是哪一种。
现在每条跳过路径都计数，并给出**下一步做什么**：

```
⛔ 1 次调用跳过了缓存（temperature>0×1）
   ——⭐ 被测系统在用采样温度。判分要可复现，
     把它的 temperature 钉成 0（mem0 默认是 0.1）
```

四种情形各有各的说法：

| 情形 | 诊断 |
|---|---|
| 没开 | `设 AMB_LLM_CACHE=1 打开` |
| 采样温度 | ⭐ 上面那条 |
| 一次 LLM 都没调 | `⚠️ 缓存无从谈起` |
| 调了但从不命中 | `⛔ 请求内容每次都不同（提示里带了时间戳？随机 id？）` |

⚠️ **区分「一次都没调」与「调了没中」很要紧**——
前者说明这一档根本不涉及 LLM，后者才是缓存有问题。

⛔ 缓存命中率也进报告首屏：

```
⚠️ **LLM 缓存命中 9/10**——⛔ 这次的延迟数不是独立测量
```

### ⚠️ 一个把我卡了很久的前提

mem0 默认 `temperature=0.1`。因为「⛔ temperature>0 时不缓存」这条规矩，
缓存**静默失效**——命中率恒为 0，**而且没有任何报错**。

⛔ 一个静默失效的优化比没有优化更糟：它让人以为已经优化过了。

⭐ 正确的修法不是放宽那条规矩，是**把 temperature 钉成 0**——
判分本来就要可复现，采样温度不该 >0。⚠️ 缓存能用只是顺带的好处。

**适用**：迭代评测代码、复现历史结果、CI。

---

## ⚠️ 还有一条：换 backbone

换一个更快的 backbone 确实能压时间，⛔ **但它改变的是测量本身**——
不同 backbone 抽出来的事实不同，归并决策也不同。

⭐ 它是**受控变量**：只要所有臂用同一个就公平。
⚠️ 但换了之后，**旧结果与新结果不可比**，backbone 必须进报告。

## 怎么组合

| 场景 | 用什么 |
|---|---|
| 第一次跑一个系统 | ⚠️ 老老实实花那个时间——⭐ **那个数字本身是结果**（[原则⑥](adapters/README.md#p6)）|
| 改了判分/套件，语料没变 | ⭐ 摄入快照 |
| 跑到一半被 OOM / Ctrl-C | ⭐ 续跑——⚠️ 原样再跑一次就行 |
| 复现历史结果 | ⭐ LLM 缓存 |
| CI | ⭐ 缓存 + 快照 + 只跑便宜的臂 |
| 发布对比结论 | ⛔ **冷跑**——缓存命中的延迟数不能当真 |
